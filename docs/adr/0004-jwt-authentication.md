# ADR-0004: JWT認証方式

## ステータス

Accepted

## コンテキスト

SFUへのアクセス制御と認可を実現するための認証方式を決定する必要がある。以下の要件がある：

- ステートレスな認証（SFUインスタンス間で状態共有不要）
- ルーム単位でのアクセス制御
- 権限レベル（admin, moderator, publisher, subscriber）のサポート
- 短時間での検証（シグナリング遅延への影響最小化）
- トークン失効の管理
- キーローテーションのサポート

## 決定

**RS256アルゴリズムによるJWT（JSON Web Token）を採用し、JWKSエンドポイントで公開鍵を配布する。**

トークンの有効期限を1時間とし、必要に応じてRedisベースのブラックリストで即座の失効に対応する。

## 検討した選択肢

### 選択肢1: セッションベース認証

**概要**: サーバーサイドにセッション情報を保持し、セッションIDで認証する。

**メリット**:

- 即座のセッション無効化が可能
- セッション情報の柔軟な管理

**デメリット**:

- 状態の共有が必要（複数インスタンス間）
- スケールの課題
- セッションストアへの依存

### 選択肢2: JWT（対称鍵 - HS256）

**概要**: 共有秘密鍵を使用してJWTを署名・検証する。

**メリット**:

- 実装がシンプル
- 検証が高速
- ステートレス

**デメリット**:

- 秘密鍵の配布が必要
- 鍵漏洩時の影響が大きい
- 発行者と検証者で同じ鍵を共有

### 選択肢3: JWT（非対称鍵 - RS256）

**概要**: RSA秘密鍵で署名し、公開鍵で検証する。

**メリット**:

- 秘密鍵は発行者のみ保持
- 公開鍵は安全に配布可能
- JWKSによる鍵管理の標準化
- キーローテーションが容易
- ステートレス

**デメリット**:

- HS256より検証が遅い（実用上問題なし）
- 鍵ペア管理の複雑さ

### 選択肢4: OAuth 2.0 / OpenID Connect

**概要**: 外部のIdPを使用した認証・認可。

**メリット**:

- 標準化されたフロー
- 既存IdPとの統合が容易
- SSO対応

**デメリット**:

- 外部依存
- レイテンシ増加（トークン検証にIdP通信が必要な場合）
- 実装の複雑さ

## 決定理由

1. **ステートレス性**: JWTはトークン自体に必要な情報を含むため、検証にデータベースアクセスが不要。SFUの水平スケールに適している。

2. **RS256の選択**:
   - 秘密鍵は認証サーバーのみが保持し、SFUは公開鍵のみで検証可能
   - 鍵漏洩のリスクが低減
   - JWKSエンドポイントで公開鍵を配布でき、キーローテーションが容易

3. **JWKSエンドポイント**:
   - 公開鍵の配布が標準化
   - キーローテーション時にSFU再起動不要
   - `kid`（Key ID）による複数鍵の同時運用が可能

4. **短いTTL + ブラックリスト**:
   - 1時間のTTLでトークン有効期間を制限
   - 緊急の失効にはRedisブラックリストで対応
   - TTL経過後は自然に失効するため、ブラックリストのサイズを制限

5. **クレーム設計**:
   - `room_id`: ルーム単位のアクセス制御
   - `permissions`: 細かい権限制御（publish, subscribe）
   - `role`: ロールベースのアクセス制御

## JWTクレーム仕様

### 必須クレーム

| クレーム  | 説明                   | 例                           |
| --------- | ---------------------- | ---------------------------- |
| `sub`     | ユーザー識別子         | `"user-123"`                 |
| `iat`     | 発行日時               | `1704067200`                 |
| `exp`     | 有効期限               | `1704070800`                 |
| `iss`     | 発行者                 | `"https://auth.example.com"` |
| `aud`     | 対象者                 | `"sfu.example.com"`          |
| `room_id` | アクセス可能なルームID | `"room-456"`                 |

### オプションクレーム

| クレーム      | 説明           | 例                                     |
| ------------- | -------------- | -------------------------------------- |
| `role`        | ユーザーロール | `"publisher"`                          |
| `permissions` | 権限リスト     | `["media:publish", "media:subscribe"]` |

## キーローテーション戦略

1. 新しい鍵ペアを生成し、JWKSエンドポイントに追加
2. 新しいトークンは新しい鍵で署名（`kid`を含める）
3. 旧鍵は7日間の猶予期間中、検証に使用可能
4. 猶予期間後、旧鍵をJWKSから削除
5. ローテーション周期: 90日

## 影響

### ポジティブな影響

- SFUインスタンス間で状態共有が不要
- 水平スケールが容易
- 公開鍵のみでの検証によりセキュリティ向上
- 標準化された鍵管理（JWKS）

### ネガティブな影響

- 即座のトークン失効にはブラックリストが必要
- JWKSエンドポイントへの依存（キャッシュで軽減）

### トレードオフ

- **即時失効 vs ステートレス性**: 完全な即時失効にはブラックリストが必要だが、短いTTLである程度軽減
- **セキュリティ vs 複雑さ**: RS256は実装が複雑だが、鍵管理のセキュリティが向上

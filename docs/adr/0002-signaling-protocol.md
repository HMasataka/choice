# ADR-0002: JSON-RPC 2.0 シグナリングプロトコル

## ステータス

Accepted

## コンテキスト

WebRTC接続の確立と管理のために、クライアントとSFU間のシグナリングプロトコルを決定する必要がある。シグナリングでは以下の操作をサポートする必要がある：

- ルームへの参加/退出
- SDP（Session Description Protocol）の交換
- ICE候補の交換
- トラックの公開/購読
- Simulcastレイヤーの制御
- サーバーからのイベント通知

プロトコル選定にあたり、以下の要件がある：

- 双方向通信（リクエスト/レスポンス + サーバープッシュ）
- 低遅延
- 型安全性（スキーマ定義可能）
- エラーハンドリングの標準化
- デバッグの容易さ

## 決定

**WebSocket上でJSON-RPC 2.0プロトコルを採用する。**

リクエスト/レスポンスにはJSON-RPC 2.0のメソッド呼び出しを使用し、サーバーからのプッシュ通知にはJSON-RPC 2.0の通知（idなし）を使用する。

## 検討した選択肢

### 選択肢1: カスタムJSONプロトコル

**概要**: 独自のメッセージフォーマットを定義する。

**メリット**:

- 完全な柔軟性
- 必要最小限の設計が可能

**デメリット**:

- 標準化されていない
- エラーハンドリングを独自定義する必要
- ドキュメント化のコスト
- クライアントライブラリを一から実装

### 選択肢2: gRPC over WebSocket

**概要**: Protocol Buffersを使用したgRPCをWebSocket上で動作させる。

**メリット**:

- 強い型安全性
- 効率的なバイナリエンコーディング
- サービス定義からコード生成

**デメリット**:

- ブラウザでの直接サポートなし（grpc-web必要）
- デバッグが困難（バイナリ形式）
- WebSocket上での動作が非標準
- 実装の複雑さ

### 選択肢3: JSON-RPC 2.0

**概要**: 標準化されたJSONベースのRPCプロトコル。

**メリット**:

- 標準仕様が存在（明確なセマンティクス）
- エラーコードが標準化
- 通知（サーバープッシュ）をネイティブサポート
- バッチリクエストをサポート
- 可読性が高い（JSON）
- 多くの言語でライブラリが存在

**デメリット**:

- バイナリより帯域効率が劣る
- 型安全性はJSON Schemaで補完が必要

### 選択肢4: Socket.IO

**概要**: イベントベースのリアルタイム通信ライブラリ。

**メリット**:

- 自動再接続
- ルーム機能内蔵
- フォールバック機構（polling）

**デメリット**:

- 独自プロトコル
- オーバーヘッドが大きい
- サーバー実装が限定的
- 標準化されていない

## 決定理由

1. **標準化**: JSON-RPC 2.0は[IETF仕様](https://www.jsonrpc.org/specification)として標準化されており、セマンティクスが明確。

2. **通知サポート**: JSON-RPC 2.0は`id`フィールドを省略することで通知（サーバープッシュ）を表現できる。これはWebRTCシグナリングの「参加者が入室した」「トラックが公開された」等のイベント通知に最適。

3. **エラーハンドリング**: 標準化されたエラーコード体系があり、アプリケーション固有のエラーコードも追加可能。

4. **デバッグ容易性**: JSONは可読性が高く、ブラウザのDevToolsやWiresharkで容易にデバッグ可能。

5. **クライアント互換性**: 多くのプログラミング言語でJSON-RPCライブラリが存在し、クライアント実装が容易。

6. **WebSocketとの親和性**: WebSocketの全二重通信とJSON-RPC 2.0のリクエスト/レスポンス+通知モデルが良く適合する。

7. **帯域幅**: WebRTCのメディアストリームと比較してシグナリングのデータ量は微小であり、JSONのオーバーヘッドは許容範囲。

## 影響

### ポジティブな影響

- 標準仕様に基づくため、実装の一貫性が保たれる
- エラーハンドリングが統一される
- 通知とリクエスト/レスポンスを同一プロトコルで表現可能
- デバッグとトラブルシューティングが容易
- JSON Schemaによる型定義とバリデーションが可能

### ネガティブな影響

- Protocol Buffersと比較して帯域効率が劣る（実用上問題なし）
- 型安全性の担保にJSON Schemaが別途必要

### トレードオフ

- **効率性 vs 可読性**: バイナリプロトコルより帯域効率は劣るが、可読性とデバッグ容易性を得る
- **柔軟性 vs 標準化**: カスタムプロトコルより柔軟性は劣るが、標準化のメリットを得る

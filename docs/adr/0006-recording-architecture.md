# ADR-0006: 録画アーキテクチャ

## ステータス

Accepted

## コンテキスト

ルーム内のメディアストリームを録画し、後から再生可能にする機能が必要である。以下の要件がある：

- 任意のタイミングで録画開始/停止
- 参加者の同意管理
- 録画ファイルのセキュアな保存
- 録画メタデータの管理（参加者リスト、同意状況）
- 長時間録画のサポート
- 複数フォーマット対応（WebM, MP4）

録画アーキテクチャには主に以下のアプローチがある：

1. クライアントサイド録画
2. サーバーサイド録画（SFU内蔵）
3. サーバーサイド録画（分離）

## 決定

**サーバーサイド録画をSFUプロセス内で実装し、録画ファイルはCloud Storageに保存する。**

録画はSFUが受信するRTPストリームをそのまま記録し、トランスコードは行わない。WebM（VP8/Opus）を主要フォーマットとする。

## 検討した選択肢

### 選択肢1: クライアントサイド録画

**概要**: 各クライアントが自身のメディアを録画し、アップロードする。

**メリット**:

- サーバー負荷なし
- 実装がシンプル

**デメリット**:

- クライアント依存（ブラウザ閉じると録画停止）
- 全参加者の録画を統合する必要
- 同期が困難
- クライアント端末の負荷
- 信頼性が低い

### 選択肢2: サーバーサイド録画（SFU内蔵）

**概要**: SFUプロセス内で録画機能を実装。受信したストリームをそのまま保存。

**メリット**:

- アーキテクチャがシンプル
- 追加インフラ不要
- 低遅延で録画開始可能
- メディアの追加コピーが不要

**デメリット**:

- SFUの責務が増える
- SFU障害時に録画も影響
- ストレージI/Oの影響

### 選択肢3: サーバーサイド録画（分離サービス）

**概要**: 録画専用のサービスがSFUからストリームを受信して録画。

**メリット**:

- 関心の分離
- 録画サービスの独立スケール
- SFUへの影響最小化

**デメリット**:

- アーキテクチャの複雑化
- 追加インフラコスト
- メディアの追加転送が必要
- 遅延増加

## 決定理由

1. **シンプルさ**: SFU内蔵方式は追加インフラが不要で、運用の複雑さを抑えられる。初期段階ではこの方式で十分。

2. **効率性**: SFUは既にストリームを受信しているため、追加のメディアコピーや転送が不要。

3. **即時性**: 録画開始/停止のリクエストに対して、即座に反映可能。

4. **コスト**: 分離サービスと比較して、追加のコンピューティングリソースが不要。

5. **将来の拡張**: 必要に応じて分離サービスへの移行は可能。現時点では過剰な複雑さを避ける。

6. **フォーマット選択**:
   - WebMはVP8/Opusを直接格納でき、トランスコード不要
   - ブラウザでの再生に対応
   - MP4が必要な場合は後処理で変換

## 録画フロー

```
1. admin が POST /api/v1/rooms/{id}/recording (開始)
2. SFU が録画開始、recordingStarted 通知を全参加者に送信
3. SFUが受信RTPパケットをWebMファイルに書き込み
4. admin が DELETE /api/v1/rooms/{id}/recording (停止)
5. SFU が録画停止、recordingStopped 通知を全参加者に送信
6. ファイルをCloud Storageにアップロード
7. メタデータをCloud Storage（metadata.json）に保存
```

## ストレージ構成

```
gs://PROJECT_ID-sfu-recordings/
└── recordings/
    └── {room_id}/
        └── {recording_id}/
            ├── media.webm      # メディアファイル
            └── metadata.json   # メタデータ
```

## 同意管理

1. 録画開始時、全参加者に`recordingStarted`通知
2. クライアントは参加者に同意UIを表示
3. 同意/拒否をサーバーに送信（オプション）
4. 同意しない参加者はルームから退出可能
5. メタデータに各参加者の同意状況を記録

## 影響

### ポジティブな影響

- シンプルなアーキテクチャで録画機能を実現
- 追加インフラなしで運用可能
- 録画開始/停止の即時反映
- トランスコードなしで効率的

### ネガティブな影響

- SFUプロセスの責務が増加
- 録画中はディスクI/Oが発生
- SFU障害時に録画データの一部が失われる可能性

### 軽減策

- 定期的なCloud Storageへのチャンク書き込み
- 録画バッファの適切なサイズ設定
- 高IOPSストレージの使用（必要に応じて）

### トレードオフ

- **シンプルさ vs 分離**: SFU内蔵で複雑さを抑えるが、責務の分離は犠牲
- **即時性 vs 耐障害性**: 即時の録画開始が可能だが、SFU障害時のリスク

## 将来の拡張

- 分離録画サービスへの移行（大規模化時）
- リアルタイムトランスコード
- ライブストリーミング連携
- 録画の部分ダウンロード

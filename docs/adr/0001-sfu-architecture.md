# ADR-0001: SFUアーキテクチャの採用

## ステータス

Accepted

## コンテキスト

WebRTCベースのリアルタイム通信システムを構築するにあたり、メディアストリームの配信アーキテクチャを決定する必要がある。主に以下の要件を満たす必要がある：

- 最大100人の参加者をサポート
- 低遅延（200ms以下）のメディア配信
- サーバーサイドでの品質制御（Simulcast/帯域幅適応）
- 録画機能のサポート
- スケーラブルな設計

WebRTCのメディア配信には主に3つのアーキテクチャパターンがある：

1. Mesh（P2P）
2. MCU（Multipoint Control Unit）
3. SFU（Selective Forwarding Unit）

## 決定

**SFU（Selective Forwarding Unit）アーキテクチャを採用する。**

SFUはクライアントからのメディアストリームを受信し、他の参加者に選択的に転送するサーバーである。メディアのトランスコードは行わず、パケットの転送のみを行う。

## 検討した選択肢

### 選択肢1: Mesh（P2P）

**概要**: 参加者同士が直接P2P接続でメディアを送受信する。サーバーはシグナリングのみ担当。

**メリット**:

- サーバーコストが最小
- 実装がシンプル
- 遅延が最小（直接通信）

**デメリット**:

- 参加者数に対してO(n²)の接続が必要
- 各クライアントのアップロード帯域がボトルネック
- 10人以上の会議には非現実的
- サーバーサイド録画が困難

### 選択肢2: MCU（Multipoint Control Unit）

**概要**: サーバーが全ストリームを受信し、合成・トランスコードして単一のストリームとして配信する。

**メリット**:

- クライアントの負荷が最小（単一ストリーム受信）
- 帯域幅の使用効率が良い
- 参加者数に関係なく一定の受信帯域

**デメリット**:

- サーバーのCPU負荷が非常に高い（トランスコード）
- サーバーコストが高い
- 遅延が増加（エンコード/デコード処理）
- 個別の品質制御が困難
- スケールが難しい

### 選択肢3: SFU（Selective Forwarding Unit）

**概要**: サーバーがストリームを受信し、トランスコードなしで選択的に転送する。

**メリット**:

- サーバーCPU負荷が低い（転送のみ）
- 個別の品質制御が可能（Simulcast）
- 低遅延（トランスコードなし）
- 録画が容易
- 水平スケールが可能

**デメリット**:

- クライアントの受信帯域がMeshより必要
- 実装の複雑さがMeshより高い
- Simulcast実装が必要

## 決定理由

1. **スケーラビリティ**: 100人規模の参加者をサポートするには、MeshのO(n²)接続は非現実的。SFUはO(n)の接続で済む。

2. **サーバーコスト**: MCUはトランスコードのためにGPUや高性能CPUが必要だが、SFUはパケット転送のみのためコスト効率が良い。

3. **遅延要件**: 200ms以下の遅延要件に対し、MCUのトランスコード遅延は許容できない。SFUは転送のみのため遅延が最小。

4. **品質制御**: Simulcastと組み合わせることで、参加者ごとに最適な品質を選択できる。

5. **録画機能**: SFUはストリームを直接受信するため、サーバーサイド録画が容易。

6. **実績**: LiveKit、Janus、Mediasoupなど、多くの本番環境で実績のあるアーキテクチャ。

## 影響

### ポジティブな影響

- CPU負荷が低く、サーバーコストを抑制できる
- 低遅延での配信が可能
- Simulcastによる適応的品質制御が実現可能
- サーバーサイド録画が実装しやすい
- 将来的な水平スケールが可能

### ネガティブな影響

- クライアントは複数のストリームを受信する必要がある
- Simulcast実装の複雑さが増す
- 帯域幅制御ロジックの実装が必要

### トレードオフ

- **シンプルさ vs 機能性**: Meshより複雑だが、スケーラビリティと機能性を得る
- **サーバーリソース vs クライアントリソース**: MCUよりサーバー負荷は低いが、クライアントの受信処理は増える

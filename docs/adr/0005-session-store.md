# ADR-0005: Redisセッションストア

## ステータス

Accepted

## コンテキスト

SFUクラスタ構成において、複数のSFUインスタンス間で共有が必要な状態を管理するストレージを決定する必要がある。共有が必要な状態には以下がある：

- アクティブなルームの一覧
- ルームとSFUインスタンスのマッピング
- 参加者セッション情報（再接続用）
- JWTブラックリスト
- レート制限カウンター

ストレージ選定にあたり、以下の要件がある：

- 低遅延（シグナリング処理に影響を与えない）
- 高可用性
- TTL（自動期限切れ）のサポート
- アトミック操作のサポート
- 運用実績

## 決定

**Redisをセッションストアとして採用する。GCP環境ではMemorystore for Redisを使用する。**

## 検討した選択肢

### 選択肢1: Redis

**概要**: インメモリデータストアで、キーバリューストア、パブサブ、データ構造をサポート。

**メリット**:

- 極めて低遅延（サブミリ秒）
- 豊富なデータ構造（String, Hash, Set, Sorted Set）
- TTLネイティブサポート
- アトミック操作（INCR, SETNX等）
- Pub/Subによるイベント配信
- クラスタモード/Sentinelによる高可用性
- マネージドサービスが豊富（Memorystore, ElastiCache）

**デメリット**:

- メモリ制限
- 永続化は限定的（RDB/AOF）
- 単一障害点になりうる（適切な構成で回避）

### 選択肢2: PostgreSQL

**概要**: リレーショナルデータベースをセッションストアとして使用。

**メリット**:

- 堅牢な永続化
- 複雑なクエリが可能
- トランザクションサポート

**デメリット**:

- Redisより遅延が大きい
- 高頻度の読み書きには不向き
- セッションデータにRDBMSは過剰
- TTLの実装が複雑

### 選択肢3: etcd

**概要**: 分散キーバリューストア、主にKubernetesの設定管理に使用。

**メリット**:

- 強い一貫性
- 分散環境に適した設計
- Watch機能によるイベント通知

**デメリット**:

- 高頻度の書き込みには不向き
- セッション管理用途には過剰
- Redisより遅延が大きい

### 選択肢4: インメモリ（ローカル）

**概要**: 各SFUインスタンスのメモリに状態を保持。

**メリット**:

- 外部依存なし
- 最も低遅延

**デメリット**:

- インスタンス間で状態共有不可
- スケールアウト困難
- フェイルオーバー時にデータ消失

## 決定理由

1. **低遅延**: Redisはサブミリ秒のレイテンシを提供。シグナリング処理のクリティカルパスに影響を与えない。

2. **TTLサポート**: セッション、ブラックリスト、レート制限カウンターは全てTTLが必要。Redisはネイティブでサポート。

3. **アトミック操作**: レート制限の実装に`INCR`と`EXPIRE`のアトミックな組み合わせが必要。Redisはこれをネイティブでサポート（Luaスクリプトも可）。

4. **データ構造**:
   - ルーム情報: Hash
   - JWTブラックリスト: Set with TTL
   - レート制限: String with INCR

5. **Pub/Sub**: SFUインスタンス間のイベント通知に利用可能（将来の拡張）。

6. **マネージドサービス**: GCPのMemorystore for Redisは高可用性構成（Standard HA）をサポートし、運用負荷を軽減。

7. **実績**: 多くのWebアプリケーションでセッションストアとしてRedisが採用されており、運用ノウハウが豊富。

## データ構造設計

### ルーム情報

```
Key: room:{room_id}
Type: Hash
Fields:
  - server_id: SFUインスタンスID
  - created_at: 作成日時
  - participant_count: 参加者数
  - state: ルーム状態
TTL: なし（明示的に削除）
```

### 参加者セッション

```
Key: session:{participant_id}
Type: Hash
Fields:
  - room_id: ルームID
  - joined_at: 参加日時
  - tracks: 公開中トラック情報（JSON）
TTL: 30秒（再接続タイムアウト）
```

**制約**: 1 participant = 1 session を前提とし、同一participantの複数同時接続は想定しない。

### JWTブラックリスト

```
Key: jwt:blacklist:{jti}
Type: String
Value: "1"
TTL: トークンの残り有効期限
```

### レート制限

```
Key: ratelimit:{type}:{identifier}
Type: String (counter)
Value: リクエスト数
TTL: ウィンドウサイズ（1分 or 1秒）
```

## 影響

### ポジティブな影響

- SFUインスタンス間でルーム情報を共有可能
- 再接続時にセッション情報を復元可能
- JWTの即時失効が実現可能
- レート制限がインスタンス横断で機能

### ネガティブな影響

- 外部サービスへの依存
- Redis障害時の影響範囲が大きい（軽減策あり）

### 軽減策

- Memorystore Standard HAによる冗長化
- 接続プール + リトライによる一時的障害への対応
- Redis障害時はJWT検証のみで動作（ブラックリストは無効）

### トレードオフ

- **外部依存 vs 機能性**: Redisへの依存が発生するが、必要な機能（TTL、アトミック操作）を得られる
- **メモリコスト vs 永続化**: インメモリのため容量制限があるが、低遅延を得られる
